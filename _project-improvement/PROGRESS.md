## 3. 給接手 AI 或人類的鐵律（不可再犯，違反者需重做該階段）

1. **禁止新增 `<style id="...">` 或 `<script id="...">` 形式的「補丁疊加」**——這正是本次 130+30 個補丁、7,829 個 `!important` 的成因。任何修改一律直接改到對應的原始選擇器/函式本體。
2. **禁止新增硬編色碼（hex）**——一律使用 `:root` 內既有或新增的語意化 CSS 變數。
3. **每個階段開始前，先讀本檔案「狀態」欄位，只做狀態為「⏳ 待執行」且編號最小的那一個階段**，不可跳階，不可一次做多階段。
4. **每個階段結束、送交人類確認前，必須完成第2節列出的5項強制品管檢查，並把檢查結果寫進本檔對應階段區塊**（格式比照第4節「階段1執行紀錄」）。
5. **未經人類明確回覆「同意/沒問題」，不可自行判定階段完成並繼續下一階段。**
6. 每個階段完成並經人類確認後，狀態改為 ✅，並提供當次「完整專案壓縮檔」（而非只給 diff），確保任何人重新解壓即可直接部署。
7. **改程式碼前先驗證，不要只憑 grep/眼睛看就下結論**——階段3就發生過「看起來像bug、實際上不是」的案例（見第6節），如果沒有多做一步查證就直接刪除，會製造出比原本更嚴重的新bug。懷疑有問題時，優先用能實際執行/解析程式碼的工具（如語法樹解析、實際跑一次程式碼）確認，而不是只憑文字比對。
8. **每次改完都要在 `_project-improvement/tests/` 留下可重複執行的自動化測試**（除非該階段完全不涉及程式碼邏輯，例如純文件整理），格式比照 `stage2-concurrency.test.js`／`stage3-admin-panel-render.test.js`：直接載入、驅動專案裡真正的原始碼去測試，而不是另外重寫一份簡化邏輯來測。
9. **「CSS規則內容/結構比對顯示完全相同」不等於「HTML標籤本身沒有被破壞」，必須分開驗證**——階段5的實際教訓：合併`<style>`標籤時因為說明註解不小心寫了字面上的`</style>`，導致標籤被瀏覽器提前截斷，但因為HTML解析的容錯機制，CSS規則的「總量」剛好還是對的，只看規則內容比對完全看不出問題。任何動到`<style>`/`<script>`標籤結構的操作，都必須同時用`verify-style-boundaries.js`／`verify-script-boundaries.js`確認標籤邊界正確，並用`visual-regression-check.py`做真實瀏覽器視覺回歸，四層驗證（規則內容比對＋標籤邊界＋碰撞檢查＋視覺回歸）缺一不可。
10. **合併/移動任何補丁前，「相鄰」或「無衝突」的判斷一定要基於逐位元組的真實位置關係，不能只看「同類型標籤之間沒有東西」**——階段5第一次嘗試就因為只檢查「兩個候選style補丁中間沒有其他style補丁」，沒發現中間其實夾著一整段`<script>`樣板字面值，合併時把中間內容整段吞掉，讓頁面直接壞掉。
11. **合併CSS規則時，絕對不能把每個屬性名稱當成互相獨立的東西處理，必須考慮簡寫屬性（`border`／`background`／`font`／`margin`／`padding`等）會連帶重設對應展開屬性的語意**——階段7的教訓：`border:1px solid ...`這種簡寫規則會連帶重設`border-color`，如果合併邏輯把`border`和`border-color`當成兩個不相干的屬性各自比對「誰最後生效」，會得出跟瀏覽器實際行為不一致的錯誤結果。更麻煩的是，**這種錯誤连「整份文件所有選擇器最終生效樣式逐一比對」這麼嚴謹的方法都抓不到**（因為比對邏輯跟合併邏輯用了同一套錯誤假設，兩邊剛好對得起來），只有真的用瀏覽器截圖比對才發現問題。任何涉及CSS規則合併/去重的工作，若沒有把握正確處理簡寫屬性語意，寧可不做，也不要冒然套用「看起來規則內容比對得起來」的結果。

## 5. 階段 2 執行紀錄（v2.3.26）

**問題**：`log-event.js`（每次登入/下載都呼叫）與 `delete-download.js`（管理者刪檔）原本都是「整包讀出 `all-events` 陣列→在記憶體改→整包寫回」，完全沒有任何併發保護。兩個請求幾乎同時發生時（例如使用者下載報告的同一瞬間，管理者正在刪除另一筆舊紀錄的檔案），後寫入的那次會用「自己讀到的舊資料+自己的修改」整包覆蓋掉，讓對方剛寫入的紀錄悄悄消失、不會有任何錯誤訊息或事後線索——這是稽核紀錄系統最不能接受的「沉默資料遺失」。同一份陣列隨紀錄數增加，每次寫入都要重寫整包資料，也是效能隱憂。

**執行內容**：
- 升級 `package.json` 內 `@netlify/blobs` 依賴版本：`^8.1.0` → `^10.7.13`（實際查證：`onlyIfMatch`/`onlyIfNew` 條件式寫入能力是從 10.0.0 才開始支援，8.x 完全沒有這個機制，無法只靠改程式碼、不升級套件版本來解決）。
- `netlify/functions/_utils.js` 新增共用函式 `updateLogsWithRetry(event, mutateFn)`：讀取時一併取得當下版本的 `etag`；寫入時帶上 `{onlyIfMatch: etag}`（第一次寫入用 `{onlyIfNew:true}`），若期間有其他請求搶先寫入，Blobs 會回傳 `{modified:false}` 拒絕這次寫入而不是被覆蓋，此時重新讀取最新版本、重新套用這次的修改再試一次，並加入「指數退避＋隨機抖動」延遲，避免大量請求同時衝突時互相卡死；最多重試 12 次，全部失敗才回傳明確的 500 錯誤（而不是靜默丟失或無限等待）。
- `log-event.js` 改用 `updateLogsWithRetry` 寫入新事件。
- `delete-download.js` 改用 `updateLogsWithRetry` 更新紀錄；並加強防呆：重試期間若發現同一筆紀錄的檔案已被另一個幾乎同時的刪除請求處理過，視為目標已達成、直接成功，不會出現令人困惑的錯誤（處理「同一筆紀錄被同時刪除兩次」的邊界情況）。
- `admin-logs.js`、`get-download.js` **完全未修改**（用 diff 逐行比對確認與 v2.3.24 原始版本一致）——這兩支只讀取 `all-events`、不寫入，不在本次競態問題範圍內。

## 8. 階段 5 執行紀錄（v2.3.29）

**內容**：合併第一批「小型、不碰`:root`、風險最低」的style補丁。實際做法：不是「移到主樣式表＋移除`!important`」（那需要對每個選擇器逐一分析跟主樣式表有沒有衝突，還沒有把握能百分之百安全），而是先做**零風險的結構合併**——把「真正逐位元組緊鄰（中間沒有任何其他內容，包含連一個空白之外的字元都沒有）」的連續小型補丁，合併成一個`<style>`區塊，CSS規則內容與相對順序完全不變，純粹減少`<style>`標籤的破碎程度。`!important`的移除留給之後更謹慎的階段處理。

**結果**：找到11串符合條件的連續補丁，共66個，合併後style標籤數從112個（111補丁+1主樣式表）減少為57個。

**★ 重要事故記錄（第一次嘗試失敗，完整記錄過程，供未來引以為戒）**：

第一版合併邏輯只檢查「兩個候選補丁中間有沒有夾雜其他*style*補丁」就當作相鄰，結果誤判了：中間如果夾著一整段**不是`<style>`標籤**的內容（例如階段3發現的那個「產生獨立下載報告」功能，整段長達數千行的`<script>`樣板字面值），因為裡面沒有任何`<style>`標籤，我的邏輯完全沒有發現「其實中間隔了一大段東西」，就把頭尾兩個相距9000多行的補丁誤判成相鄰，合併時直接把中間那一大段內容整個吞掉——第一次測試載入時，瀏覽器回報`body`文字長度變成0，整個頁面壞掉。

修正：改成「必須真正逐位元組緊鄰（中間的字元只能是空白）」才視為同一串，重新計算後才是正確的11串66個。

**★ 第二次事故（同一階段內，緊接著發生，同樣完整記錄）**：修正上面那個問題後，我在合併後的`<style>`標籤裡加了一段說明註解，內容提到「少了幾組`</style><style id="...">`邊界」——**這段註解文字本身就包含字面上的`</style>`**！HTML的標籤掃描是在瀏覽器認得出「這是寫在CSS註解裡」之前就發生的，只要看到`</style`這幾個字元，就會把當下的`<style>`標籤提前結束。因為HTML解析對這種錯誤有容錯（後面文字會被當成別的東西繼續解析），最後拼出來的「CSS規則總量」剛好還是2416條不變——**我原本用「CSS規則內容/AST比對」驗證，顯示完全一致就以為沒問題，但直接用瀏覽器檢查實際的`<style>`元素，才發現合併出來的區塊內容只剩61個字元（應該有數千字元），標籤已經被截斷了，只是HTML的容錯機制讓CSS規則本身沒有真的消失，換到別的地方去了而已**。

## 10. 階段 7 嘗試紀錄（本次未產生新版本，`index.html` 仍停留在 v2.3.30，未受影響）

**目標**：處理`global-final-readability-polish`（341條規則、2422行）與`inlined-non-generic-product-polish`（447條規則、3233行）這兩個超大型補丁。

**第一次嘗試（已證實不安全，未套用）**：發現這兩個補丁內部有大量「同一個選擇器在同一個補丁裡出現好幾次」的情況（例如`.btn-primary,.btn-success`同一個補丁內就出現3次，分別對應歷史上不同的主題實驗）。嘗試把同一補丁內重複的選擇器合併成一條規則，每個屬性取「最後生效」的值（正確處理`!important`優先權）。

**驗證發現的問題**：
- 用「整份文件1701個選擇器的最終生效樣式逐一比對」這個目前為止最嚴謹的方法檢查，**顯示完全相同、0個不符**。
- 但用真實瀏覽器截圖比對（`visual-regression-check.py`），screen-3出現0.4%的像素差異，**明顯超過雜訊基準值**，工具正確地把它標記為需要人工確認。
- 放大比對截圖後，實際看到「整理交付報告」按鈕從長方形圓角變成完全的膠囊/藥丸形狀，邊框顏色也不一樣。

**根本原因（重要教訓）**：`.btn-primary,.btn-success`這個選擇器在補丁內先後出現3次，其中一次設定了`border-radius:999px`與`border-color:var(--impact-blue)`（各自獨立的屬性），最後一次（最終生效的主題）設定的是`border:1px solid rgba(125,211,252,.34)`這個**簡寫屬性**——在真正的CSS規則裡，設定`border`簡寫會連帶重設`border-color`／`border-width`／`border-style`，等於會蓋掉前面單獨設定的`border-color`。但我的合併邏輯是「每個屬性名稱各自獨立比對最後出現的值」，把`border`和`border-color`當成兩個互不相干的屬性處理，沒有理解簡寫屬性會連帶重設對應的展開屬性——所以錯誤地把已經該被蓋掉的`border-color:var(--impact-blue)`跟`border-radius:999px`一起留了下來，跟最終應該生效的樣式混在一起，才會產生視覺差異。

**這次的重要啟示**：**「整份文件所有選擇器的最終生效樣式逐一比對完全相同」這個方法，只要牽涉到CSS簡寫屬性（`border`／`background`／`font`／`margin`／`padding`等）跟對應的展開屬性混用，就可能給出「看起來完全正確」的假陽性結果**——因為比對邏輯本身跟合併邏輯犯了同一種「不懂簡寫屬性語意」的錯，兩邊剛好用同一套錯誤假設，所以互相對得起來，卻跟瀏覽器真正的行為不一致。這是比階段5的兩次事故更難發現的一種錯誤類型：**規則內容比對過關、標籤結構也沒截斷，純粹是CSS語意本身理解錯誤，只有真的用瀏覽器截圖比對才抓得到**。已經把這條寫進第3節鐵律。

**結論**：這個「合併同一補丁內重複選擇器」的做法，若要做對，需要先建立一份完整的CSS簡寫屬性展開對照表（`border`→`border-width`/`border-style`/`border-color`，`background`→`background-color`/`background-image`/...等等），正確處理簡寫屬性連帶重設展開屬性的語意，才能安全地判斷「這個屬性到底最後是誰生效」。這是一個明顯更大、更容易再犯錯的工程，**這次先不做**，避免為了處理⑥類問題（重複程式碼）反而製造新的④類問題（配色/樣式錯誤）。

**已嘗試過、確認安全但沒有額外空間的做法**：用階段5同樣的「真正逐位元組緊鄰」邏輯，重新檢查目前剩下的56個style補丁與30個script補丁，**沒有找到任何新的可安全合併的相鄰組合**（階段5已經把能用這個方法處理的都處理完了）。

**本階段目前狀態**：`index.html`未被修改，仍是v2.3.30。已將以上發現如實記錄，等待與使用者確認下一步方向（例如：是否要投入更多工建置正確處理簡寫屬性的合併邏輯；或者接受這兩個超大型補丁維持現狀，把它們列為已知限制；或者改用其他更安全的方式，例如針對特定幾個容易確認的選擇器手動逐一處理，而不是自動化整批合併）。

## 12. v2.3.32 執行紀錄（接續 v2.3.31）

### ［階段2］429 重試退避策略修正 —— 這是 Agnes 被限流／帳號暫停的直接成因之一

**問題**：`fetchWithRetry()` 的 `RETRYABLE_STATUSES` 同時包含 `429` 與 `503/502/504`，
但退避計算只有一套：`Math.pow(2,attempt)*1500`，也就是 1.5 秒 → 3 秒 → 6 秒，
而且**完全沒有讀取回應中的 `Retry-After` 標頭**。

這兩種狀態碼的語意完全不同：
- `503/502/504` 是「伺服器此刻忙線或閘道異常」，通常幾秒後就恢復，短退避是對的；
- `429` 是「你這段時間內的用量已超過配額」，**1.5 秒後再打一次必然再吃一次 429**。
  在被限流的當下連續敲三次門，正是第三方服務把帳號判定為濫用、進而暫時停用的典型觸發條件。

**修法**（全部集中在 `fetchWithRetry` 前方，未新增任何補丁區塊）：
1. 新增 `parseRetryAfterMs()`：支援 `Retry-After` 的兩種合法格式（秒數、HTTP 日期），
   格式無效時安全回傳 null 而不丟例外。
2. 新增 `computeRetryWaitMs()`：429 的等待下限為 8 秒起跳並指數成長（8/16/32 秒），
   與 5xx 的 1.5/3/6 秒分開；伺服器若有給 `Retry-After`，**以伺服器為準且只會更久不會更短**
   （避免伺服器說等 1 秒就真的只等 1 秒又撞上限流）。
3. 加入 25% 隨機抖動，避免多個分頁或多位使用者在同一瞬間一起重試造成二次尖峰。
   此處刻意使用 `Math.random()` 而非階段3 的 `SimRandom`——**抖動的價值就在於各用戶端彼此不同步，
   可重現反而有害**。已在 stage3 測試中把這一處列為「刻意保留的真亂數」並註明理由。
4. 若伺服器要求的等待時間超過 60 秒，`computeRetryWaitMs()` 回傳 null，
   `fetchWithRetry` 直接返回該回應停止重試，由上層顯示明確錯誤——
   而不是讓使用者盯著 loading 空等，或繼續敲門讓限流狀況惡化。

**驗證**：新增 `tests/stage2-rate-limit-backoff.test.js`，直接擷取專案真實原始碼驅動，
以假 fetch 與假計時器驗證「實際等了多久」，**19 項全數通過**，涵蓋：
Retry-After 三種格式解析、429 與 503 退避節奏分離、伺服器指示優先、下限保護、
超過上限停止重試、抖動存在且幅度受控、端對端連續 429 後重試成功、400 不重試。

## 13. v2.3.33 執行紀錄：分段生成 + 逐段落地暫存（階段2 最後一塊）

### 為什麼這才是 429／逾時的治本修法

v2.3.31 把 system prompt 從 14,291 縮到 11,951 字元，處理的是**輸入端**。
但單次請求的 `max_tokens` 是 **13,000**，輸出端才是大頭。單一請求越大：
① 越容易被第三方供應商判定為異常大流量而觸發速率限制；
② 生成時間越長，越容易撞上逾時；
③ **一旦被截斷或中途失敗，整份分析全部重跑**，前面已經生成好的內容全部作廢。

### 執行內容

**1. `buildSystemPrompt()` 新增 `scope` 參數**（`'full'` ／ `'market'` ／ `'analysis'`）
- `'market'`：競品／SWOT／知覺圖。不帶時間軸、全漏斗、五層分析規則。
- `'analysis'`：五層分析。不帶競品存續查核、競品分析、來源連結查證、SWOT 規則，
  以及只為查競品而存在的權威來源類別（商工登記／上市櫃財務／進出口／專利）。
- JSON schema 改為依 scope 組裝（`schemaParts`），不再要求模型產出這一段用不到的欄位。
- **向後相容鐵則**：不傳 `scope` 時輸出必須與改版前逐字相同。
  已用 v2.3.32 的 `index.html` 做 8 組輸入 × 2 種 hasRealSearch 的逐字元比對，**全數相同**；
  並在 `stage2-prompt-size.test.js` 中加入常駐斷言（不傳 scope ≡ scope='full'、
  完整版仍含 13 個規則段落與 8 個頂層 schema 欄位），確保未來不會被改回去。

**2. 分段排程與合併**
- `planAnalysisSegments()`：決定單次或分段、每段的 scope 與輸出額度。
  競品段刻意排第一——那是最容易失敗、最耗時的一段，先打浪費最少。
- `mergeAnalysisSegments()`：合併成與單次完整分析**完全相同形狀**的物件，
  下游渲染器一行都不用改。特別處理「後段的 undefined／null 不可洗掉前段已取得的內容」。
- 加值技能模組的輸出歸到五層分析段（`buildDynamicPromptTail` 新增 scope 參數），
  競品段不重複產出，避免白白吃掉該段的輸出額度。

**3. 逐段落地暫存 `AnalysisCheckpoint`（IndexedDB）**
- `runId` 由使用者輸入內容雜湊而來 → 同一份輸入才命中暫存，改動任一輸入即不會誤用舊結果。
- 暫存保留 24 小時後自動失效。
- **每個方法都自帶 try/catch 並回傳安全值**：隱私模式或舊瀏覽器沒有 IndexedDB 時，
  一律當作「沒有暫存」繼續跑完，絕不可因為暫存失敗而讓整份分析失敗。

**4. 保守的啟用策略（重要）**
預設**只對 Agnes 啟用分段**，Claude／Gemini 維持原本單次路徑完全不動。
理由：這兩條路徑目前運作正常且已長期驗證，而本次環境無法對真實 API 做端對端測試——
沒有把握就不改動正常運作的路徑，是鐵律第 7 條的精神。
其他供應商可由 `window.SEGMENTED_ANALYSIS = true` 手動開啟。

**5. 順帶修掉一個交叉指涉錯誤**
五層分析段原本會殘留一句「且引用時仍須完全遵守下方【來源連結查證】規則」，
但該段落在這個 scope 下根本不存在——等於對模型下達指向不存在段落的指令。
已改為依 scope 條件輸出。**這是分段化最容易產生、又最不容易被發現的一類錯誤**
（prompt 語法完全正確、程式也不會報錯，只有把產出的 prompt 整份讀過才看得到），
後續若再新增 scope，務必一併檢查所有「上方／下方【某段落】」的交叉指涉。

## 16. v2.3.37-testing 執行紀錄：回應使用者提問——Agnes 路由確認 ＋ RPM 觀測與軟性節流

使用者截圖顯示 Agnes 持續遇到 `rate_limit`（429），並提出兩個具體問題。

### 問題①：輸入 Agnes API Key 後，程式是不是誤打到 Claude？

**答案：不是，程式邏輯上不可能。** `callAI()` 的分派邏輯如下（原始碼逐字如此）：

```js
async function callAI(...){
  const provider=getProvider();
  if(provider==='gemini') return await callGemini(...);
  if(provider==='agnes')  return await callAgnes(...);   // ← agnes 分支直接 return
  return await callClaude(...);                          // ← 只有前兩個條件都不成立才會走到這裡
}
```

`provider==='agnes'` 那一行寫在 `callClaude` 呼叫之前，且該分支會直接 `return`，
不存在「先打 Agnes 又不小心接著打 Claude」的路徑。已新增
`stage-agnes-rpm-and-routing.test.js`，用真實原始碼端對端執行 `callAI('agnes')`，
證明 `callAgnes` 恰好執行 1 次、`callClaude`／`callGemini` 皆為 0 次。

使用者提供的截圖裡，診斷面板本身也顯示「供應商／模型：Agnes AI / agnes-2.0-flash」，
這是程式在**實際執行當下**記錄下來的真實供應商別，與上面的程式邏輯互相印證，
不是程式碼看起來對但實際執行不同。

### 問題②：目前每分鐘是否超過 RPM 20？

**答案：從這裡看不到使用者實際的即時流量，但新增了觀測工具，下次發生時就能直接看到數字。**
Claude 本身無法看到使用者瀏覽器裡實際發生的網路請求時序，因此無法「代替驗證」他們
當下是否真的超過 20 RPM。但可以做到兩件事：

1. **精確觀測**：新增 `AgnesRateTracker`，記錄「每一次真正送出去的 Agnes HTTP 請求」——
   注意這裡刻意包含 `fetchWithRetry` 內部的重試，因為供應商計算 RPM 配額是按實際送達
   伺服器的請求數，不是按「使用者眼中的一次操作」；一次分析在分段模式下有 2 段，
   若中途觸發 429 又各自重試 2 次，光是一次分析最多就可能送出 6 次請求。
   這個數字現在會即時顯示在「本次分析執行紀錄」診斷面板，也會出現在兩個
   「複製完整除錯資訊」按鈕的輸出文字中。**下次再遇到 429，畫面上就會直接寫著
   「過去60秒內對 Agnes 的實際 API 呼叫次數：N 次」**，不必再用猜的。
2. **軟性節流**：新增 `AGNES_RPM_SOFT_LIMIT = 18`（比常見的 RPM 20 低，留緩衝）。
   當滾動 60 秒視窗內的請求數已達到這個警戒線，**新發起**的請求（不含重試，
   重試本身已經有 8/16/32 秒的退避等待）會先等到視窗內最舊一筆請求「滿 60 秒」、
   額度自然釋放後才送出，而不是立刻送出去再吃一次 429、又觸發一輪更長的重試等待。
   這是客戶端能做到的最大努力，實際的 RPM 上限仍以 Agnes 帳號本身的方案設定為準——

**這次實作過程本身就是一堂關於「自製驗證工具也可能有系統性盲點」的課**，
連續踩到、也連續修正了四個問題，如實記錄：

1. **合併工具誤判「落在 script 字串內的字面樣式標籤文字」**：本檔案的
   `downloadPackage()` 報告匯出範本、admin 面板動態插入樣式的字串，本身就內嵌了
   完整的樣式標籤文字（屬於報告自己的獨立文件，不是本文件的真實標籤）。第一版
   合併工具的 naive 掃描把這些誤判成真標籤，導致一個合併區塊的內容被錯誤地
   跨越報告範本拼接，第一次執行後用「合併前逐字記錄的原始片段清單」比對，
   立刻發現內容對不上，**在套用前就攔了下來**，隨即改用排除報告範本範圍的修正版。

2. **修正後仍誤判「落在 HTML 註解裡的字面樣式標籤文字」**：本檔案 v2.3.29 版本
   歷史裡有一句「合併成11個樣式區塊」的說明文字，用反引號包住了字面的樣式標籤
   語法作為範例——naive 掃描不理解自己身處註解之中，一樣會把它當成真標籤。
   再次用逐字比對抓到、修正。

3. **修正後把「帶有其他屬性的外部腳本標籤」誤當成可合併補丁**：Chart.js 的外部
   腳本載入標籤同時帶有 `defer`、`src`、`onerror` 三個屬性（`onerror` 是 CDN
   載入失敗時的降級機制）。前兩版工具只要標籤緊鄰就合併，合併後的開始標籤是
   寫死的 `id` 專用格式，會把原本的 `src`／`onerror` 屬性整個蓋掉，
   等同悄悄弄丟離線降級機制。這次是用**功能性的 diff**（合併前後比對所有 inline
   事件屬性數量）抓到的，而不是內容比對——這提醒了一件事：內容逐字比對只能
   證明「文字沒丟」，證明不了「屬性語意沒丟」，兩種驗證都需要。
   修正為：只有「只帶 `id` 屬性、不帶任何其他屬性」的標籤才視為可合併補丁，
   遇到其他標籤視為阻隔物，會截斷它前後的相鄰性判斷，不會被誤併。

4. **量測工具本身的系統性誤差（不影響任何實際功能，但影響所有基準數字）**：
   前三個問題修正後，用同一套邏輯重新量測「全文件真正有幾個 style 標籤」，
   發現本專案長年沿用、甚至路線圖原文證據索引裡就寫著的「80個 style 標籤」，
   從一開始就是用天真正則掃描量出來的，混入了報告匯出範本內嵌文字的虛高計數；
   真正的頂層 style 標籤數其實是 57 個。**這不代表任何程式行為被動過**
   （報告範本本來就是獨立文件，混入計數只是統計誤差），但意味著本專案至今
   所有文件裡引用「79」「80」這個數字的地方，量測基準都需要更正。
   已一併把 `verify-tag-boundaries-nodeps.js`／`check-inline-js-syntax.js`
   兩支診斷工具升級為 comment-aware 的 tokenizer，避免未來的量測繼續沿用
   錯誤基準；並在自己新增的版本歷史說明裡，刻意避免直接寫出尖括號標籤語法，
   改用文字描述（這個習慣本身也是這次踩坑學到的教訓——差點連自己新寫的
   說明文字都因為提到範例標籤語法而重演同一類問題，所幸在套用前的語法檢查
   就被攔了下來）。

**最終驗證方式**：每一次合併都以「合併前逐字記錄的原始片段」manifest 做精確比對，
而不是事後用正則反推內容是否遺失；額外用 inline 事件屬性數量的功能性 diff
交叉驗證屬性語意未被破壞。新增 `tools/raw-html-tokenizer.js` 作為所有相關工具

### 為什麼只做這一小塊，不做整個階段5

階段5完整範圍是三欄工作區重寫＋RWD斷點系統整併，牽動的 CSS／DOM 範圍極廣，

### 追查過程

一開始以為「locked 步驟點了沒反應」是真的邏輯缺陷，追進 `navigateFlowStep()`
才發現：點擊 locked 步驟時，程式本來就會呼叫 `toast(getLockedStepMessage(n))`

兩者疊加：游標說「不能按」，視覺上按鈕文字被蓋住看不到內容——使用者當然會
判斷這是個死掉的按鈕，不會去點，也就永遠看不到那則其實已經寫好的說明。

### 修正內容

- 游標統一改為 `pointer`（JS inline style 與樣式表兩處都改，避免只改一處

- 遮罩從「蓋滿整顆按鈕的不透明文字」改為「右上角一個帶鎖頭 emoji 的小徽章」，

- **`canAccessStep()`／`navigateFlowStep()`／`getLockedStepMessage()` 三個

## 20. v2.3.41-testing 執行紀錄：修正歸因模擬頁籤空白過大（使用者截圖回報）

### 問題

使用者截圖顯示歸因模擬頁籤的長條圖（3個管道）下方留了一大片空白，才接到
「相對於『目前假設平均分配』…的建議調整方向」那段文字。

### 根因

歸因模擬的長條圖是用 `svgBarChart()` 產生的純 SVG，高度依管道數量精確計算
（3-6個管道大約 100-250px），本身沒有問題。問題出在包住它的容器 div 用了
`class="chart-box"`——這個 class 名稱同時也被主要分析頁的 3 個 Chart.js
canvas 大圖表（預算配置、漏斗預估、情境分析）共用。樣式表裡專門給那些
canvas 大圖表用的一條規則：

```
.chart-box{height:34rem!important;min-height:34rem!important;...}
```

把「所有」`.chart-box` 都強制設成 34rem（約544px）高，不管實際內容多高。
歸因模擬的 SVG 明明只有 100-250px，卻被這條規則硬撐到 544px，
下面自然空出一大片空白——這正是使用者截圖看到的狀況。

### 修正

歸因模擬的圖表容器多加一個 `attrib-svg-chart-box` class，另外寫一條
`.chart-box.attrib-svg-chart-box{height:auto!important;min-height:0!important}`。
兩個 class 組合的選擇器，specificity 高於任何單一 `.chart-box` 規則
（即使雙方都用 `!important`，同一重要性層級內仍是比 specificity，
兩個 class 一定贏過一個 class），因此能正確覆蓋，且完全不影響其他 3 個
仍然需要固定高度的 Chart.js canvas 大圖表（它們的容器沒有多加這個新 class，
規則不會套用到它們身上）。

### 驗證

### 提醒接手者

`.chart-box` 這個 class 名稱目前身兼兩種完全不同用途（canvas 大圖表的固定
容器／各種小型 SVG 圖表的自適應容器），未來如果又有新的小圖表沿用
`chart-box` 這個名稱、卻沒有额外加區分 class，很可能重演同一個問題。
較長期的解法是把這兩種用途拆成不同的 class 名稱（例如 `.chart-box-fixed`
／`.chart-box-auto`），但這需要逐一檢查全站所有 `chart-box` 使用處，
屬於較大範圍的改動，這次先用最小風險的方式解決使用者當下回報的具體問題。
