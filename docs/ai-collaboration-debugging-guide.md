# 給非IT／非工程背景使用者：如何讓 AI 直接處理問題，而不是自己一步步排除

這份文件記錄「策引 AI Google 登入無法使用」這次的完整除錯經驗，並整理成一套往後可以直接套用的溝通方式，讓你下次遇到類似問題時，能請 AI 直接動手查、動手改，而不是自己在瀏覽器裡一直照著指示操作。

---

## 一、這次事件的最終結論（給未來的你或其他工程師參考）

**症狀**：點擊「使用 Google 帳號登入」按鈕完全沒有反應，沒有跳出任何視窗，Console 也沒有紅字錯誤。

**繞了一大圈查的方向（後來證實都不是問題）**：
- Netlify 後台 Identity／Google 外部登入設定 → 確認過，設定是對的
- `/.netlify/identity/settings` 端點 → 確認過，回應正常，Google 確實已啟用
- Console 手動執行 `netlifyIdentity.open('login')` → 有執行、回傳 `undefined`（這其實是正常的，不是錯誤）
- Network 分頁檢查請求 → 沒有發現任何失敗的請求

**真正的根本原因**：
Netlify Identity 這個登入元件本身有一個**官方已知的臭蟲**（GitHub：`netlify/netlify-identity-widget` issue #94「Iframe do not appear on top」、#67）。當網頁上有其他 `position:fixed` 且 z-index 很高的全螢幕元素時（本專案的登入前置遮罩 `#auth-gate` 的 z-index 是 `99999`），Netlify Identity 彈出的登入小視窗**會被蓋在下面、完全看不到**——但它其實有正常開啟，只是「隱形」了。

這就是為什麼從「後端設定」「Console 錯誤訊息」的角度怎麼查都查不出問題：因為根本沒有報錯，是**純粹的 CSS 疊層順序問題**，跟 Netlify 設定、Google 設定、網路連線都無關。

**修法**：強制把 Netlify Identity 登入視窗的 z-index 設為 CSS 允許的最大值 `2147483647 !important`，蓋過網站上所有其他元素。同時加了一個「改用直接跳轉登入」的備用連結（直接導向 `/.netlify/identity/authorize?provider=google`），作為萬一 widget 本身還有其他問題時的備案。

**這次能快速找到答案的關鍵**：使用者提供了「另一套已經確定能正常運作的系統」（HR 履歷比對系統）的原始碼，裡面的開發者早就踩過同一個坑、還在註解裡寫清楚了原因與修法。**直接比對兩套系統的差異，比從零開始猜測快得多。**

## 二、為什麼一開始會繞遠路——給非工程背景使用者的教訓

一開始的排查方式，是請你（使用者）一步步去做：打開 DevTools、切到 Console、手動打指令、切到 Network 分頁、截圖回報……這種做法在你是工程師、或至少熟悉瀏覽器開發工具時很有效率，因為工程師可以自己判斷「這個結果代表什麼、下一步該查哪裡」。

但如果你不是工程師，這種方式會有兩個大問題：
1. **每一輪來回都要等你截圖、等你操作**，一個問題可能要花上幾十分鐘甚至幾小時，而且很容易在中途操作錯誤（例如點錯分頁、複製到不完整的內容）。
2. **你自己看不出截圖裡的線索代表什麼**，等於是在「盲目執行 AI 的指令」，卻沒辦法自己判斷方向對不對，一旦某一步操作有誤差，AI 也很難即時發現。

真正有效率的做法，其實是：**從一開始就把「動手查」和「動手改」的工作都交給 AI，你只負責提供 AI 需要的原始素材（程式碼、錯誤畫面、已知能正常運作的對照範例），而不是照著 AI 的指示在瀏覽器裡操作。**

## 三、往後遇到類似問題，建議的溝通方式

### 原則 1：一開始就把「原始碼」交出來，不要只描述症狀

❌ 不理想的問法：
> 「登入按鈕點了沒反應，怎麼辦？」

✅ 建議的問法：
> 「這是我的專案壓縮檔，登入按鈕點了沒反應，麻煩你直接打開程式碼檢查，不要叫我在瀏覽器操作，你能查的都自己查，查不到的部分（例如需要看畫面實際反應）再跟我要。」

**原因**：AI 能直接讀取、搜尋、比對整個程式碼庫，這比你口頭描述症狀、AI 用猜的快非常多。這次能一次找到根本原因，靠的正是直接比對兩套系統的原始碼差異，而不是靠你在瀏覽器裡回報的任何截圖。

### 原則 2：如果你有「已經能正常運作的類似系統」，一開始就一起提供

這次能夠快速解決，關鍵在於使用者後來提供了「另一套系統」的原始碼作對照。**如果一開始就提供，會省下前面一大段來回排查的時間。**

以後只要遇到「這個功能在 A 系統壞掉，但類似功能在 B 系統是好的」這種情況，第一時間就把兩邊的程式碼都給 AI，請它直接比對差異，而不是先讓 AI 用一般性推測的方式排查 A 系統。

### 原則 3：需要「看瀏覽器實際反應」的部分，用工具讓 AI 直接操作瀏覽器，而不是你手動截圖回報

如果 Claude 的對話環境有提供瀏覽器操作能力（例如 Claude for Chrome 這類擴充功能），可以直接請 AI：
> 「請你直接幫我打開這個網址、點這個按鈕、檢查 Console 和 Network 的結果」

這樣 AI 可以自己看到即時結果、自己判斷下一步，不需要你在中間截圖傳來傳去，也不會因為你操作步驟不同而讓 AI 誤判。

### 原則 4：明確授權 AI「直接動手改，不要只給建議」

非工程背景的使用者常見的心態是「先問清楚原因，再自己動手改」，但這樣反而多了一層「你要看懂修法、自己動手改程式碼」的門檻，而這正是你不擅長的部分。

✅ 建議在一開始就講清楚：
> 「你直接改程式碼、直接打包給我下載，我只負責上傳到網站，不用跟我解釋太多技術細節，除非是需要我自己按什麼設定的部分。」

### 原則 5：修復後，請 AI 順手更新版本號、寫清楚修復紀錄

這樣即使以後換了不同的 AI 對話、或找別的工程師接手，程式碼裡的註解和 README 版本紀錄都能一眼看出「這個問題什麼時候修的、為什麼這樣修」，不用重新從頭排查一次。這次的修復已經同步做了這件事（見 `index.html` 開頭註解與 `README.md` 版本紀錄）。

## 四、下次可以直接複製使用的開場白範本

```
我不是工程師，不熟悉程式碼跟瀏覽器開發工具。附件是我的專案完整壓縮檔（或：我的網站網址是＿＿＿）。

問題是：＿＿＿（描述症狀，例如「按鈕點了沒反應」「頁面打不開」等）

請你：
1. 直接打開/檢查程式碼找原因，不要一開始就要我去瀏覽器操作或截圖
2. 如果你手上有瀏覽器工具，直接幫我操作測試
3. 如果我有其他「類似功能但正常運作」的系統，我會一併提供給你比對，你直接比對兩邊程式碼差異
4. 找到原因後直接幫我改好程式碼、打包成新的壓縮檔給我下載
5. 只有在真的需要我親自操作的地方（例如網站後台設定），才明確列出步驟叫我做，其餘都你直接處理
```

## 五、如果沒有「對照組系統」時，退而求其次的做法

不是每次都剛好有一套「已經能動的類似系統」可以比對。如果沒有，建議：
- 一開始就把**完整專案原始碼**（不要只給部分檔案）交給 AI，讓 AI 能看到全貌
- 明確授權 AI 主動上網搜尋這個技術／套件是否有「已知問題」（像這次的 Netlify Identity z-index 臭蟲，其實是一個在 GitHub 上公開记录多年的已知問題，早一步搜尋就能少走很多冤枉路）
- 把你能取得的**任何畫面截圖、錯誤訊息**都一次提供齊全，而不是分批一張一張來——這樣 AI 能一次看到完整脈絡，減少來回次數
